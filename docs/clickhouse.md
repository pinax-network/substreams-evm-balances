# ClickHouse: the `db_out` of each balance package

[`native/balances`](../native/balances/README.md) and
[`erc20/balances`](../erc20/balances/README.md) each ship their `map_events`
and a `db_out` in one spkg. Each `db_out` writes its half of the ClickHouse
tables of substreams-evm `evm-balances` v0.3.4 into its own database. The SQL
is upstream's and each spkg embeds its half, so `substreams-sink-sql setup`
needs only the package. The tables and the row format equal the RPC-era
database's, so a new database can take that history by partition copy.

```
Clock ─────────────────────┐
native/balances map_events ┴─▶ db_out ─▶ DatabaseChanges ─▶ substreams-sink-sql ─▶ <chain>:evm-balances-native@<version>
Clock ─────────────────────┐
erc20/balances map_events ─┴─▶ db_out ─▶ DatabaseChanges ─▶ substreams-sink-sql ─▶ <chain>:evm-balances-erc20@<version>

blocks
native_balances ──mv_historical_native_balances──▶ historical_native_balances_state ──▶ historical_native_balances (view)
erc20_balances  ──mv_historical_erc20_balances──▶  historical_erc20_balances_state  ──▶ historical_erc20_balances (view)
```

| Package | spkg and release tag | BSC database | Tables |
| --- | --- | --- | --- |
| `evm_balances_native` (`native/balances`) | `evm-balances-native-v<version>` | `bsc:evm-balances-native@<version>` | `native_balances`, `blocks`, `historical_native_balances_state`, `mv_historical_native_balances`, `historical_native_balances` |
| `evm_balances_erc20` (`erc20/balances`) | `evm-balances-erc20-v<version>` | `bsc:evm-balances-erc20@<version>` | `erc20_balances`, `blocks`, `historical_erc20_balances_state`, `mv_historical_erc20_balances`, `historical_erc20_balances` |

**Why two packages** (owner, 2026-10-13). Native records every balance change
and should rarely change once synced; ERC-20 is inference and keeps improving.
Separate packages have separate versions, databases and resyncs, so an ERC-20
fix never resyncs native. Native stops on any block it doubts and ERC-20 never
fails a block: in one package a native refusal also stopped ERC-20. The Token
API's native routes read only the native tables and its ERC-20 routes only the
ERC-20 tables, so it reads two databases per network.

The combined `evm-balances` package (v0.4.0 to v0.6.1, one `db_out` for both
tables in one database, `bsc:evm-balances@v0.6.1`) is retired; v0.6.1 is its
last release, and its source is in git history at `5101e32`.

Not ported: the PostgreSQL variant, `scripts/verify-balances.sh` (a harness

Why `sink:` sits in the package manifest: imports never carry sink config, so
upstream's `clickhouse/substreams.yaml` wrapper (`use: db:db_out`) is only
useful for several sinks over one `db_out`, for example a later PostgreSQL
variant. The sink type is `sf.substreams.sink.sql.v1.Service`, the only one
`substreams-sink-sql` accepts. Its `schema` takes exactly one file, hence the
concatenated `schema.sql`.

The imported `evm-balances-sink-protodefs` bundle supplies both descriptors
without network access. Its SQL definitions use the canonical
`sf/substreams/sink/sql/v1/deprecated.proto` path, which matches the current
CLI's built-in copy and still supplies the definitions to older SQL sink
readers; the older `services.proto` path declared the same message names and
made the GUI's strict protobuf registry reject the package. Its
`DatabaseChanges` descriptor comes from the pinned 5.0.0 encoder, so the GUI
shows `value` and `update_op`. See [descriptor provenance and rebuild
instructions](../proto/sink/SOURCES.md).

Changes against upstream `db_out`:
- **One table set per package.** Upstream's one `db_out` writes both; here each
  package writes its own table, its history and `blocks`.
- **No params.** Upstream's `hex`/`tron_base58` encoding param is gone; addresses are always hex.
- **No genesis-clock patch.** It covers block 0 of Ethereum, Arbitrum and Boba,
  whose clock has no timestamp; `db_out` fails there. BSC block 0 has one.
- **Errors instead of a panic** on a missing clock timestamp.
- **Fail-closed row checks** (see [Rows](#rows)).
- **`substreams-database-change` 5.0.0** (buffa, substreams 0.8.0) in place of
  upstream's 3.0.0. The rows are the same. On the wire, field 2 of `Field`
  keeps its number (`new_value` in 3.0.0, `value` in 5.0.0), field 3
  (`old_value`) was always empty, and every field now also carries
  `update_op = UPDATE_OP_SET` (field 4). The SQL sink uses only the name and
  value of a CREATE's fields.

## Rows

| Table | Package | Key | Columns | One row per |
| --- | --- | --- | --- | --- |
| `native_balances` | native | `address` | `address`, `balance`, `block_num`, `block_hash`, `timestamp` | `NativeBalance` of `map_events` |
| `erc20_balances` | erc20 | `(contract, address)` | `contract`, `address`, `balance`, `block_num`, `block_hash`, `timestamp` | `Balance` of `map_events` |
| `blocks` | both | `block_num` | `block_num`, `block_hash`, `timestamp` | block that wrote a balance row of this package |

- **Operation.** Every row is a CREATE, which ClickHouse inserts. `minute` is
  `MATERIALIZED` by ClickHouse.
- **Values.** Addresses are `0x` + lowercase hex, `block_hash` is `0x` + the
  clock id, `timestamp` is the clock's seconds and `balance` is the map's
  `amount`, an exact decimal.
- **Order.** Balance rows, then the `blocks` row. Columns are matched by name:
  `DatabaseChanges` field order is unstable (`substreams-database-change`
  keeps a row in a `HashMap`, in 5.0.0 as in 3.0.0), so `db_out` sorts them by
  name.
- **Fail closed.** The block fails instead of writing on an ERC-20 row without
  a contract, an address that is not 20 bytes, an amount that is not a decimal
  `uint256`, or a missing timestamp. The sink would store such values as wrong
  numbers or abort on them.
- **Independent copies.** Each package keeps its own copy of the row helpers,
  so neither package's hashes depend on the other.

## Build and deploy

```sh
cargo test --locked -p native-balances           # or -p erc20-balances
make -C native/balances build schema             # WASM and clickhouse/schema.sql
make -C native/balances install-sink             # the supported substreams-sink-sql, v4.13.0
export SUBSTREAMS_SINK_DSN='clickhouse://<user>:<password>@<host>:9000/<database>'   # create <database> first
export SUBSTREAMS_API_KEY=...
make -C native/balances setup                    # idempotent: 2 tables, 1 state, 1 MV, 1 view, cursors
make -C native/balances dev START_BLOCK=<S>
```

The same targets exist for `erc20/balances`. Committed spkgs come from CI's
"Package hashes" artifact, never from a local `make pack`: a macOS build has
other module hashes than CI's Linux build.

- **Supported sink.** [pinax-network/substreams-sink-sql
  v4.13.0](https://github.com/pinax-network/substreams-sink-sql/releases/tag/v4.13.0),
  commit `933a187`
  ([#120](https://github.com/pinax-network/substreams-evm-balances/issues/120)).
  `install-sink` builds it from a clone of the tag, because the fork's
  `go.mod` keeps the upstream module path and `go install <path>@<tag>`
  cannot fetch it. Upstream StreamingFast has its own `v4.13.0` (`5a43292`)
  without these fixes, so pin the commit, not the tag name.
  `substreams-sink-sql --version` must name commit `933a187`; `setup` and
  `dev` refuse any other build. The image
  `ghcr.io/pinax-network/substreams-sink-sql:v4.13.0` is built from the same
  tag.
- **Build first.** `substreams pack` embeds the WASM without building it, and
  `setup` reads the YAML, so every target builds the package and regenerates
  `schema.sql`. Run in the package directory, cargo builds the package alone,
  with its own dependency features.
- **Start block.** Native starts at block 0: it emits the genesis allocations
  there. Use a height qualified for the intended network; incomplete Extended
  blocks or ambiguous persisted native data still stop the stream.
- **Reorgs: an undo buffer, not final blocks** (owner, 2026-10-13). The sink
  runs with `--undo-buffer-size`, as the Token API live sinks do (BSC: 5, the
  Makefile's `UNDO_BUFFER_SIZE`), and without `--final-blocks-only`, so rows
  arrive a few blocks behind head instead of after finality. ClickHouse cannot
  revert written rows (the sink only logs UNDO), so the buffer holds the
  newest blocks back: a fork inside it is dropped before anything is written.
  A deeper fork stops the sink with `cannot undo down to last valid Block`;
  restarted from its cursor, it continues on the canonical chain, and the
  rows it wrote for the orphaned blocks stay. That is an accepted risk. Step 1
  of each package's `check-replays-and-completeness.sql` reports such heights
  as blocks with two hashes.
- **Production flags.** `dev` uses upstream's per-block flush. For production
  use the [Token API settings](#token-api-live-sinks-bsc), and drop
  `--development-mode` and `--on-module-hash-mistmatch=warn` (the fork's
  spelling; the default `error` stops on a changed `db_out`). From v4.13.0 the
  flush interval no longer changes what is stored: at any interval ClickHouse
  receives one row per key and block, so the OHLC state sees every row. Older
  sinks kept only the last row per key within a flush, which made historical
  open/high/low/`transactions` depend on the interval (never the `FINAL`
  balances); databases they wrote keep that history.
- **DSN.** Pass it shell-expanded and quoted, as the Makefile does. `${VAR}`
  placeholders inside the DSN are not expanded for the connection, and parse
  errors echo the DSN; keep passwords out of shared logs.
- **CLI alternative.** `substreams sink clickhouse setup substreams.yaml`
  (Database Changes mode) creates the same DDL. It rejects the old CLI-sink
  flags (`--sink-info-folder`, `--cursor-file-path`, `--spool-*`) and refuses
  `--undo-buffer-size 0` on ClickHouse.

## Token API live sinks (BSC)

Each package is released by its own tag and the Token API runs one live sink
per package. The live sink takes the release's package as `SPKG_URL`, with the
variables that name the database:

| Variable | Native | ERC-20 |
| --- | --- | --- |
| `ASSET` | `evm` | `evm` |
| `TYPE` | `balances-native` | `balances-erc20` |
| `VERSION` | `v<version>` | `v<version>` |
| `SPKG_URL` | `https://github.com/pinax-network/substreams-evm-balances/releases/download/evm-balances-native-v<version>/evm-balances-native-v<version>.spkg` | `https://github.com/pinax-network/substreams-evm-balances/releases/download/evm-balances-erc20-v<version>/evm-balances-erc20-v<version>.spkg` |

The databases are `bsc:evm-balances-native@<version>` and
`bsc:evm-balances-erc20@<version>`, next to the RPC-era
`bsc:evm-balances@v0.3.x`. The Token API reads one balances database per
network today. With [pinax-api#601](https://github.com/pinax-network/pinax-api/pull/601),
a network's `dbs-config.yaml` entry can name both databases next to
`balances`:

```yaml
bsc:
  balances-native: bsc:evm-balances-native@<version>
  balances-erc20: bsc:evm-balances-erc20@<version>
```

Its native routes (`/balances/native`, `/holders/native`, `/tokens/native`,
`/balances/historical/native`) then read the native database and the others
the ERC-20 database; a side without its key keeps reading `balances`, so each
database can cut over on its own. On BSC, run each sink with
the flags of the Token API's BSC balances live sink (2026-10-13); other chains
use other values, and only BSC is documented here:

```sh
substreams-sink-sql run "$SUBSTREAMS_SINK_DSN" "$PKG" <start-block>: \
  -e bsc.substreams.pinax.network:443 \
  --undo-buffer-size=5 \
  --live-block-flush-interval=20 \
  --batch-block-flush-interval=1000 \
  --batch-row-flush-interval=50000 \
  --live-block-time-delta=3m0s \
  --idle-timeout=5m \
  --on-module-hash-mistmatch=error
```

| Flag | BSC | Effect |
| --- | --- | --- |
| `--undo-buffer-size` | 5 | blocks held back from head; a deeper fork stops the sink (see [Reorgs](#build-and-deploy)) |
| `--live-block-flush-interval` | 20 | flush every 20 blocks once live |
| `--batch-block-flush-interval` | 1000 | flush every 1,000 blocks while catching up |
| `--batch-row-flush-interval` | 50000 | or once 50,000 rows are buffered |
| `--live-block-time-delta` | 3m0s | a block within 3 minutes of wall-clock counts as live |
| `--idle-timeout` | 5m | reconnect after 5 minutes without data |
| `--on-module-hash-mistmatch` | `error` | refuse a cursor of another `db_out` |

None of these changes what is stored: at any flush interval ClickHouse
receives one row per key and block.

## Cutover and backfill

The [cutover contract](initialization-and-completeness.md) states what each
database holds after the cutover: what an absent row means, which pairs can be
stale, what replays do, when a database is complete, how it compares with the
RPC-era database, and which initialization paths exist. Each package's
database is cut over on its own.

1. Stop the RPC-era sink; its cursor gives its last block, `S-1`.
2. Set up a fresh database and start the package at `S`.
3. Run the package's `clickhouse/examples/backfill-from-rpc-database.sql`: a
   DDL check, a boundary check and three partition copies (`blocks`, the
   balance table and its state table). Either check throws on failure, so a
   run of the whole file stops before it copies anything. Partition copies do
   not fire the materialized views, so `transactions` is not double-counted,
   and `AggregatingMergeTree` merges the windows that span `S`.

- **Schema first.** Compare `SHOW CREATE TABLE` in the RPC-era database with
  v0.3.4 (step 0 does). An unmerged v0.3.5 variant on upstream branch
  `fix/balances-holders` (`EPHEMERAL` `block_hash`, `is_deleted`, another
  engine, holders views) cannot be attached.
- **`blocks`.** The RPC-era `blocks` lists blocks with any balance row, native
  or ERC-20, so both databases take the same history of it.
- **Separate databases.** Never copy `cursors`, and never create a table
  without a primary key inside a sink database: the sink refuses to start.
- **Another server.** Load the RPC-era data into same-schema staging tables
  without views, then attach from those.

## What changes after the cutover

- **Native rows.** Only accounts with a persisted balance change, from the
  genesis allocations at block 0 on. The RPC era emitted every candidate
  account, unchanged ones included, so there are fewer rows and lower
  `transactions`. The zero address can appear.
- **ERC-20 rows.** Inferred: coverage and precision are
  [measured](../erc20/balances/README.md#measured), not qualified.
  `(contract, holder)` pairs the inference does not emit keep their RPC-era
  value after a partition copy from the RPC-era database; in a database
  synced from genesis they have no row (#123).
- **`blocks`.** Rows only for blocks with output of that package.
- **Failure scope.** A native refusal (incomplete or ambiguous persisted data)
  stops only the native sink; the ERC-20 sink goes on.

## Sink behaviour

- **Insert-only.** UPDATE and DELETE are errors; UNDO is ignored.
- **Replays.** A flush writes table by table, then the cursor, which is an
  asynchronous insert the sink does not wait for. A crash, a lost cursor row
  or a retried flush stores rows again: `blocks` (plain `MergeTree`) can get
  duplicate rows and `transactions` counts the rows again; FINAL, open, close,
  high and low do not change. Detect, repair or accept them as the
  [contract](initialization-and-completeness.md#5-replays) describes.
- **`transactions`** counts the rows inserted per window. With v4.13.0 that is
  one row per key and block at any flush interval; older sinks made it depend
  on the flush cadence.
- **Raw rows.** ClickHouse's default `optimize_on_insert` collapses a key
  repeated within one INSERT into a `ReplacingMergeTree`, so balance-table rows
  read without `FINAL` can show one row per key per flush. The OHLC state still
  receives every row, and `FINAL` is unaffected.
- **No chain id.** No table stores one: use one database per network and
  package.
- **Cursor.** Keyed by the `db_out` module hash.

## Monitoring

A producer change that loses ERC-20 evidence fails no block: inference only
emits fewer rows
([#116](https://github.com/pinax-network/substreams-evm-balances/issues/116)).
ERC-20 rows per block is the signal. `erc20_balances` keeps one row per pair
after merges, so count the rows inserted into the OHLC state, per hour. The
ERC-20 database's `blocks` lists only blocks with ERC-20 rows, so it cannot
count the blocks that lost theirs: take the blocks from the native database,
where nearly every block has a row because transactions pay fees.

```sql
SELECT hour, ifNull(erc20_rows, 0) / blocks AS erc20_rows_per_block
FROM (SELECT toStartOfHour(timestamp) AS hour, uniqExact(block_num) AS blocks
      FROM `bsc:evm-balances-native@<version>`.blocks
      WHERE timestamp > now() - INTERVAL 8 DAY
      GROUP BY hour) AS b
LEFT JOIN (SELECT timestamp AS hour, sum(transactions) AS erc20_rows
      FROM `bsc:evm-balances-erc20@<version>`.historical_erc20_balances_state
      WHERE interval_min = 60 AND timestamp > now() - INTERVAL 8 DAY
      GROUP BY hour) AS e USING (hour)
ORDER BY hour
```

- An hour with blocks but no ERC-20 row reads 0 instead of disappearing.
- The value is approximate: replays inflate `transactions` (above). Replayed
  `blocks` rows do not count twice.
- The current hour is partial.

Alert when a complete hour falls below an owner-chosen fraction of the
trailing 7-day median. The alert lives in ops (Grafana), not in this
repository.
